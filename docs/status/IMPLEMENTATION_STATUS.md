- **M0-6 worker messaging spike (#9, merged):** the main process starts a background **worker process** at launch. A "Worker check (M0 spike)" panel shows its real state. The worker only runs **M0 spike methods** (`spike.echo`, `spike.slowCount`) and does no product work.
  - Electron `utilityProcess` (ADR-0012), built by electron-vite through a `?modulePath` import (`out/main/chunks/index-<hash>.js`). It's a separate OS process, so a crash or hang can't take main down.
  - Channel: main hands the worker a private `MessagePort` in one `connect` message. Only main and the worker hold it, so no localhost server is involved (§7.2).
  - Protocol (`src/common/contracts/worker-protocol.ts`): Zod envelopes `request`/`cancel` → `ready`/`result`/`error`, with a random UUID per request. Both sides check size (256 KiB, UTF-8 JSON, shared `json-size.ts`, now also used by the IPC router) and schema. Main also validates the worker's results.
  - Cancellation: an `AbortSignal` or timeout settles the request at once and sends `cancel`. The worker aborts that request's `AbortController`. Late replies are dropped and counted (`staleRepliesDropped`).
  - Crash: on an unexpected exit, every pending request fails with `worker_crashed`, and the crash count and exit code are kept and logged. **Nothing is retried.** The next request starts a fresh worker. A deliberate stop (quit) fails pending requests with `worker_stopped` and isn't counted as a crash.
  - Logic with no Electron imports: `src/worker/dispatcher.ts` and `src/main/runtime-bridge/worker-bridge.ts`. Electron glue: `src/worker/index.ts` and `runtime-bridge/utility-transport.ts`.
  - New **M0 spike** IPC commands:
    - `runtime.workerStatus` (no payload)
    - `runtime.workerCheck` (optional `cancelAfterMs` 10–5000, default 100): echo, then a slow count cancelled in flight, then an echo that reads how many requests are still active.

- **M1-3 schema v2 + repositories (#30, merged as PR #40):** the database now has its first product tables. No UI or IPC uses them yet (M1-6/M1-7 add the commands).
  - Migration 2 adds `profile_settings`, `worlds` and `projects`. All three are STRICT and have `created_at`, `updated_at` (UTC) and `revision`.
  - CHECK constraints: names trimmed and 1–80 characters, slug IDs, semver template versions, `#rrggbb` avatar colours, preferences a JSON object of at most 16 KiB, profile ID `default` or a UUID (ADR-0014).
  - Project status is `active`, `archived` or `trashed`. A table CHECK keeps it consistent with `archived_at`/`trashed_at`.
  - `projects.world_id` is a foreign key (`ON DELETE RESTRICT`). Index `projects_by_world_status`, which the query planner uses.
  - `ProfileSettingsRepository`, `WorldRepository` and `ProjectRepository` are the only code that touches these tables. Every update takes an expected revision (optimistic concurrency, lesson 012).
    - A stale revision fails with `revision_conflict` (plus the current revision) and changes nothing.
    - Other stable codes: `not_found`, `already_exists`, `invalid_input`, `invalid_transition`.
    - Each update is one `UPDATE … RETURNING` statement. Since M1-4, the writes that touch a graph entity too run in `withSavepoint`, which callers can still wrap in their own transaction.
  - Rename keeps the project ID. Archive and trash are status + timestamp changes, and there is no delete method. Restoring from trash returns a project to archived if it was archived, else active (ADR-0016). A trashed project can't be edited.
  - Input is validated before SQL: code-point lengths that match SQLite; control, invisible spoofing and unpaired-surrogate characters refused; canonical IANA timezones (bare offsets like `+02:00` refused); preferences limited to plain JSON data, 16 KiB and 32 levels.

- **M1-2 profile storage (#29, merged as PR #45):** the app now has real local profiles on disk. There is no profile UI or command yet (M1-6, M1-8, M1-9).
  - `userData/profiles-index.json` (schema v1) holds only profile IDs, display names and the last-used ID. Strict Zod schema: unknown keys refused, IDs unique, list not empty, last-used must be listed, names follow the usual name rules. Read-only on load; a bad file is reported (`unreadable`, `invalid_json`, `invalid_shape`, `newer_version`) and **never** rewritten.
  - Writes are atomic: temp file (`wx`) in the same folder → fsync → rename, retried up to 5 times over ~0.5 s for Windows `EPERM`/`EBUSY`/`EACCES`. Leftover `profiles-index.json.<hex>.tmp` files are removed at startup.
  - Profile IDs: `default` (legacy, M0) or a lowercase UUID, as the branded type `ProfileId` (`src/main/storage/profiles/profile-id.ts`). `profilePaths` re-checks the ID at runtime, so no path is ever built from raw index text.
  - Startup (`openStartupProfile`, `src/main/storage/profiles/startup.ts`):
    - index present → open the last-used profile. Its `app.sqlite` must exist and be already migrated (version > 0), else `ProfileDataMissingError`;
    - no index, only `profiles/default/app.sqlite` → adopt as "Default" (keeps launch history);
    - no index, no profile data → create "Default" with a new UUID (ADR-0017);
    - no index but other profile databases exist → stop with `ProfilesIndexMissingError` (your decision: fail closed);
    - an M0 `default` folder without `app.sqlite` is refused, not adopted.
    - The DB is opened and migrated before a new index is written, so a failed first launch leaves no index.
  - `src/main/index.ts` shows a separate path-free dialog for a damaged/newer index, a missing index, missing profile data, and other DB failures, then quits. Nothing is deleted.

- **M1-4 graph entity IDs (#31, merged as PR #44):** every world and project now has a graph entity: the stable node ID the Realm Atlas (M2) and imports will build on (GRAPH_MODEL §30.5, ADR-0018). No UI or IPC uses it yet.
  - Migration 3 adds `graph_entities` (STRICT): its own UUID, `kind` (`world`/`project`), `world_id`, `project_id` (project entities only), `ownership` (`app_owned`/`external`), `source_locator` (nullable, required for `external`, ≤ 1024 characters), `tombstoned_at`, timestamps and `revision`. There are **no name or layout columns**.
  - A composite foreign key `(project_id, world_id) → projects (id, world_id)` keeps a project entity in its project's own world. Partial unique indexes allow one entity per world and one per project.
  - Upgrading a v2 database backfills entities for existing worlds and projects (UUIDs built with `randomblob`). Trashed projects start tombstoned.
  - `WorldRepository.create` and `ProjectRepository.create` insert the record and its entity in one transaction. `ProjectRepository.trash` sets the tombstone and `restoreFromTrash` clears it, in the same transaction as the status change. Archiving doesn't tombstone. `GraphEntityRepository` has no delete method.
  - `withSavepoint` (`database.ts`): opens a transaction, or nests in one that `withTransaction` opened through a SQLite SAVEPOINT. If SQLite cancels the whole transaction by itself (disk full, I/O error), the transaction is marked aborted: further writes throw `TransactionAbortedError` and it won't commit, so writes never autocommit half a unit. It refuses to join a transaction it didn't open.

- [ADR-0031](../adr/0031-atlas-view-preferences-and-docked-drawer.md) (M2-12 #77): Realm Atlas display choices per world live under `atlasViews` in `preferences_json` via `profile.atlasView.get/update` (no revision, max 32 worlds); `graph_view_states` waits for layout coordinates; the narrow drawer docks as a grid column so it can't cover editing controls
- [ADR-0030](../adr/0030-react-flow-v13.md) (Dependabot PR #55, merged as 918a758): `@xyflow/react` 12.12.1 → 13.0.2. `onNodesChange` now receives a `NodeChangeset` object (we read `getByType('select')`), and `colorMode` became `forceColorMode`; the CSS file and CSP are unchanged
- [ADR-0029](../adr/0029-project-links-in-project-relations.md) (M2-11 #76): project links live in a dedicated `project_relations` table (composite FKs keep both ends in one world), not a general `graph_edges`; the source → target order is the direction (A→B ≠ B→A, no direction column); links of a trashed project are kept but hidden from `graph.worldConnections` and its counts; `relation.remove` takes an expected revision; deterministic 150-node / 300-edge cut with omitted counts
- M2-9 (user choices via AskUserQuestion, no ADR, recorded in `docs/sessions/2026-11-23-library-panel.md`): "Hide world view" is a session-only toggle, not a saved setting; Placed / Not placed is a second "On map" filter group that combines with the status filter and loads every page while on.
- [ADR-0028](../adr/0028-comfort-preferences-and-building-labels.md) (M2-14 #79): comfort preferences have their own `profile.preferences.get/update`, stored under `comfort` in `preferences_json` and merged without a revision (last write wins), so camera saves never make settings forms conflict; one camera per world (view centre + zoom, max 64, least recently saved dropped); building name labels stay a fixed size on screen and hide below 0.35×; `placement.list` reports `projectName`
- [ADR-0027](../adr/0027-ui-ux-polish-and-art-milestone.md) (roadmap, #93): new **M8 — UI/UX polish and art integration** before MVP; old M8–M11 are now M9–M12 (MVP = M9); art from PixelLab MCP under a per-batch budget the user approves; M5 only proves the art pipeline with a small slice.
