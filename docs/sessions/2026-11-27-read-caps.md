# 2026-11-27: Profile and world limits on read (#61)

## Task
#61: the 50-profile and 100-world limits were only checked when creating. A restored, imported or hand-edited profile list, or a database with more worlds, made `profile.list` / `world.list` fail their own output check (`internal_error`). The session loader then stopped, and **the whole app opened on an error screen** even though the data was fine. This is a release gate before import commit (IMP-2) and restore. Branch `fix/61-read-caps`.

## What happened
- Checked GitHub first for a branch, PR or assignee on #61 (none). Commented "Started on branch" and assigned it to X4stra (the user approved).
- Read the list handlers, contracts, `ProfileService.list`, the session loader and the profile and world pickers.
- **Slice 1** (`fix(profiles): keep profile and world lists usable…`):
  - `ProfileListOutput` and `WorldListOutput` gain `omittedCount`.
  - `profile.list` returns at most 50 profiles. The active one is always included, and index order is kept.
  - `world.list` returns at most 100, in creation order.
  - The main log records counts only, never names.
  - Integration tests (51 profiles, 101 worlds):
    - The list is `ok`.
    - The active profile is listed whether it's first or last in the index.
    - The index file is byte-for-byte unchanged, and all 101 world rows remain.
    - Creating more is still refused.
    - `omittedCount` is 0 at exactly the limit.
- **Slice 2** (UI):
  - `omittedNotice()` gives the wording, for example *"Showing 50 of 51 profiles. The other one is kept on this computer; nothing was deleted."* It's unit-tested.
  - The profile picker shows it under the list, and the world picker shows the world version in the top bar.
  - E2E `tests/e2e/list-limits.spec.ts`:
    - Onboard normally, close the app, and seed 50 extra profiles plus 100 extra worlds, as a restore would.
    - Relaunch: the main screen opens and both notices show.
    - After closing: the index is unchanged and all 101 worlds are still there.

Routine choices (no question asked):
- **The active profile is always listed,** even if it's the 51st in the index, so the user can see where they are.
- **Which worlds show:** the first 100 in creation order, the list's existing order. Omitted worlds can't be reached from the UI until something is removed or archived. That's acceptable for a restore-only situation, and the notice says so.
  - *Correction (2026-11-27, after merge):* the app has no world archive command and no profile delete, so omitted worlds and profiles can't be reached from the UI at all today. They stay on disk, untouched. The in-app notice never promised a way back. Tracked in #139.
- **`profiles-index.ts` is unchanged.** It already reads any number of entries, which keeps startup lenient.
- **The E2E seeds worlds through the app's own `WorldRepository`** (Node 24 has `node:sqlite`). Only the `world.create` limit, an IPC rule, is bypassed; every database rule still holds.

## Why it looks like this (learning notes)
- **An output check can lock users out.** Validating replies is good (lesson 003 covers the router checking its own output), but if stored data can legitimately exceed the reply's limit, the reply must be *bounded* rather than *refused*. The Realm Atlas graph already does this with `omittedNodes` / `omittedEdges`.
- **Bounded, never destructive.** The fix only changes what is *shown*. Deleting the extras to fit would silently lose a user's data (PRODUCT_RULES §3.1).
